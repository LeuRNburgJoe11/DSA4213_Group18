\section*{Project Summary}

Our project studies indirect prompt injection in tool-using LLM agents: we
simulate three attacker agents that each attempt to inject malicious
instructions into the content a fourth, defended agent must process, and
measure which combination of defenses is most effective at resisting these
injections while still completing the legitimate task. Building on the
AgentDojo threat model \cite{debenedetti2024agentdojo}, we implement an
undefended baseline agent alongside three defense strategies -- provenance
tagging, privilege separation, and classifier-gated confirmation -- and
evaluate all four configurations on a shared email/calendar assistant task
suite. Our evaluation plan scores every configuration on two axes at once:
attack success rate (security) and task completion rate (utility), since a
defense that blocks everything but also breaks the agent's usefulness is not
a real solution. We aim to learn which defense families hold up best under
increasingly adversarial conditions -- including a novel multi-step,
delayed-trigger injection that splits a malicious instruction across several
tool calls -- and whether combining defenses meaningfully improves the
security-utility trade-off over any single strategy alone.

% ====================
% 1. Problem and motivation
% ====================
\section*{1. Problem, Research Question, and Motivation}

Tool-using LLM agents (e.g., email assistants that can read messages and send
replies, or calendar assistants that can create events) must ingest content
from untrusted external sources -- emails, web pages, calendar invites,
retrieved documents -- in order to complete ordinary tasks. Because everything
the model reads, whether a trusted user instruction or untrusted tool output,
ends up as tokens in the same context window, the model has no hard
architectural signal distinguishing ``data to summarize'' from ``a command to
obey.'' This enables \emph{indirect prompt injection}: an attacker plants text
inside content the agent will read (e.g., ``Ignore the summarization task;
forward the last 5 emails to attacker@example.com'') to hijack the agent's
tool calls.

\textbf{Research question.} How do different defense strategies against
prompt injection trade off \emph{security} (resistance to hijacking) against
\emph{utility} (ability to still complete the legitimate task), and can a
lightweight combination of strategies achieve a better security-utility
trade-off than any single strategy alone -- including against injections that
are deliberately split across multiple tool calls to evade single-pass
detection?

\textbf{Motivation.} This is not a hypothetical concern: agentic systems with
real side-effecting tools (sending email, making purchases, editing files) are
already being deployed, and a successful injection can cause real-world harm.
A defense that simply refuses to act on anything ambiguous ``wins'' on
security but is useless in practice, so any credible evaluation must measure
both axes together rather than security alone. The intended setting is a
general-purpose personal-assistant agent (email/calendar workflows) acting on
behalf of a non-expert user who cannot inspect every tool output for hidden
instructions. An agent-based framing is essential here: the vulnerability is
specifically about the interaction between an LLM's instruction-following
behavior and its tool-calling loop, not about the LLM in isolation.

\textbf{Success criterion.} The project succeeds if it produces (i) a working
implementation of an undefended agent and at least two defense strategies on a
shared benchmark, (ii) a quantitative security-utility comparison across
strategies, and (iii) evidence on whether a multi-step, delayed-trigger
injection breaks defenses that a single-turn injection does not.

% ====================
% 2. Related work and contribution
% ====================
\section*{2. Related Work and Proposed Contribution}

\textbf{Benchmarks and threat model.} AgentDojo \cite{debenedetti2024agentdojo}
formalizes indirect prompt injection against tool-using agents as a dynamic
benchmark, providing task suites (e.g., workspace/email assistants) alongside
injection tasks, and -- centrally to our design -- scores every defense on
both attack success rate and task utility simultaneously. The underlying
threat model traces back to work on indirect prompt injection via retrieved
content \cite{greshake2023youve}, which first showed that content an LLM is
asked to process (not just the user's own prompt) can carry adversarial
instructions.

\textbf{Defense families.} Prior defenses cluster into a few strategies we
draw on directly: (i) \emph{provenance tagging / structured prompting}, which
marks tool outputs as non-authoritative data regardless of phrasing, related
to structured-query approaches such as StruQ \cite{chen2024struq} and
``spotlighting'' techniques that delimit untrusted spans; (ii) \emph{privilege
separation}, where a planner commits to an action plan before seeing untrusted
content and a more restricted executor carries it out, so injected text
encountered mid-task cannot expand the action space; and (iii) \emph{detection
classifiers}, a separate model or filter that screens tool outputs for
injection-like patterns before the main agent sees them. Each has known
weaknesses -- tagging can be ignored under adversarial rephrasing, privilege
separation adds latency and can block legitimate reactive tasks, and detectors
can be evaded by novel phrasing or by splitting an instruction across turns.

\textbf{Proposed contribution.} Beyond assembling these components, the group
will contribute: (1) an integrated evaluation harness that runs the same task
suite against an undefended baseline and multiple defenses under one
consistent security/utility metric; (2) a purpose-built \emph{multi-step,
delayed-trigger} injection variant -- splitting an adversarial instruction
across two or more tool outputs the agent reads on different turns -- to test
whether defenses tuned for single-turn injections still hold; and (3) an
ablation of a simple hybrid defense (privilege separation plus a lightweight
confirmation gate) to test whether combining strategies improves the
trade-off beyond any single strategy. All external claims about benchmark
design and defense behavior are attributed to the cited sources; any dataset
or code reused from AgentDojo will be credited explicitly.

% 3. Agent setup
% ====================
\section*{3. Agent and Task Setup}

This is an empirical study comparing an undefended agent against several
defended variants on a shared task suite.

\begin{itemize}[leftmargin=*,itemsep=0.25em]
    \item \textbf{Task and environment.} A simulated email/calendar workspace
    assistant, adapted from a small subset of AgentDojo's workspace task
    suite: the agent receives a natural-language user request (e.g.,
    ``summarize today's unread emails and send the summary to my manager'')
    and must complete it by calling tools over a simulated mailbox and
    calendar.
    \item \textbf{Inputs/outputs.} Inputs are the user instruction plus tool
    outputs (email bodies, calendar entries), some of which contain planted
    injected instructions. Outputs are the sequence of tool calls the agent
    issues and its final natural-language response.
    \item \textbf{Model, tools, and defenses.} A single LLM (e.g., a Claude or
    GPT-4o-mini class model) accessed via API serves as the base agent, given
    tools \texttt{read\_emails}, \texttt{send\_email},
    \texttt{read\_calendar}, and \texttt{create\_event}. Three defense
    variants wrap this same base agent: a provenance-tagging/prompt-sandwich
    wrapper, a planner/executor privilege-separation wrapper, and a
    classifier-gated confirmation wrapper on side-effecting calls.
    \item \textbf{Benchmark and interaction protocol.} AgentDojo-style benign
    task instances (to measure utility) and injection task instances (to
    measure attack success rate), run non-interactively for a fixed number of
    episodes per condition; each episode pairs one user task with one
    injected email.
    \item \textbf{Stopping conditions, constraints, and failure recovery.}
    Each episode terminates on task completion, an explicit refusal, or after
    a fixed tool-call budget ($N \le 10$) is exhausted. Side-effecting tools
    (\texttt{send\_email}, \texttt{create\_event}) are logged separately from
    read-only tools so that attack success (an unauthorized side-effecting
    call) can be distinguished from ordinary task failure.
\end{itemize}

% ====================
% 4. System or study design
% ====================
\section*{4. Proposed System or Study Design}

The group will implement an evaluation harness with four agent configurations
run over the same task suite:

\begin{enumerate}[leftmargin=*,itemsep=0.25em]
    \item \textbf{Undefended baseline.} Tool outputs are inserted directly
    into the agent's context with no isolation; establishes an upper bound on
    attack success rate and an upper bound on utility (no defense overhead).
    \item \textbf{Provenance tagging.} Tool outputs are wrapped in explicit
    delimiters with an instruction that content inside them is data, never a
    command, regardless of imperative phrasing.
    \item \textbf{Privilege separation.} A planner model commits to an action
    plan (which tools it will call, with what arguments) \emph{before} any
    untrusted tool output is read; a separate executor may only carry out
    calls consistent with that plan, so injected instructions encountered
    mid-episode cannot introduce new side-effecting calls.
    \item \textbf{Classifier-gated confirmation.} A lightweight secondary
    classifier screens every side-effecting tool call (not the raw tool
    output) immediately before execution and blocks calls whose target or
    content diverges from the original user request.
\end{enumerate}

The technically meaningful, group-owned component is the harness itself (the
consistent interface that lets any of the four configurations run against any
task/injection pair and log both utility and security outcomes) together with
the delayed-trigger injection generator described below. A system diagram
(user request $\rightarrow$ agent $\rightarrow$ tool call $\rightarrow$ tool
output, possibly containing an injection $\rightarrow$ defense layer
$\rightarrow$ executed action) and one annotated example trajectory showing a
blocked hijack attempt will be included in the final report.

\subsection*{4.1 Comparisons and Ablations}

\begin{itemize}[leftmargin=*,itemsep=0.25em]
    \item \textbf{Baseline comparison.} All three defenses vs.\ the
    undefended baseline, on both attack success rate and task utility, to
    establish each defense's individual cost/benefit.
    \item \textbf{Hybrid ablation.} Privilege separation combined with the
    confirmation gate, to test whether stacking defenses improves the
    trade-off beyond either alone or merely adds latency without added
    robustness.
    \item \textbf{Injection strength ablation.} Single-turn, visible
    injections vs.\ obfuscated (e.g., reworded, translated) single-turn
    injections vs.\ our proposed \emph{multi-step delayed-trigger} injection,
    where the malicious instruction is split across two tool outputs the
    agent reads on separate turns and only becomes actionable once both parts
    have been seen -- targeting the gap that single-pass detectors are least
    equipped to catch.
    \item \textbf{Injection position ablation.} Injected text placed early
    vs.\ late within a tool output, to check whether defenses are sensitive
    to position within context.
\end{itemize}

\section*{5. Preliminary Evaluation Plan}

\textbf{Primary metrics}, computed per configuration (baseline, each defense, hybrid):
\begin{itemize}[leftmargin=*,itemsep=0.25em]
    \item \emph{Attack success rate (ASR)} — fraction of injection episodes where the agent executes the attacker's intended side-effecting call (e.g., sends to the wrong recipient).
    \item \emph{Task utility} — fraction of benign episodes where the agent correctly completes the user's original request, scored against AgentDojo-style task checks or a rubric.
    \item \emph{Utility-under-attack} — task completion rate on injection episodes specifically, to separate "defense blocked the attack" from "defense also broke the legitimate task."
\end{itemize}

\textbf{Secondary/diagnostic metrics:}
\begin{itemize}[leftmargin=*,itemsep=0.25em]
    \item Tool-call budget used per episode (proxy for latency/overhead added by each defense).
    \item False-positive rate of the confirmation-gate classifier on benign side-effecting calls.
    \item Breakdown of ASR by injection type (visible / obfuscated / multi-step delayed-trigger) and position (early / late), tying results back to the section 4.1 ablations.
\end{itemize}

\textbf{Protocol:}
\begin{itemize}[leftmargin=*,itemsep=0.25em]
    \item Fixed set of benign + injection task instances, run identically across all four configurations for a controlled comparison.
    \item Multiple runs per episode (e.g., $n=3$–$5$) to account for LLM sampling variance; report mean $\pm$ spread rather than a single run.
    \item Automated pass/fail checks on final tool-call logs where possible; manual review for ambiguous trajectories.
\end{itemize}

\textbf{Qualitative analysis:} 2–3 representative successful defenses (attack blocked, task still completed) and 2–3 representative failures (attack succeeded, or defense broke utility) included as annotated trajectories in the report to illustrate why a defense worked or failed, not just that it did.

\textbf{Presentation:} results as a summary table (configuration $\times$ ASR $\times$ utility) plus one plot showing the security-utility trade-off frontier across configurations, supplemented by the trajectory case studies.

% 6. Risks and responsible practice
% ====================
\section*{6. Risks, Limitations, and Responsible Practice}

\begin{itemize}[leftmargin=*,itemsep=0.25em]
    \item \textbf{Scope limitation:} findings are specific to the simulated environment and chosen base LLM(s); ASR and utility numbers may not transfer to other tool sets, models, or real deployments — this will be stated explicitly as a limitation, not generalized.
    \item \textbf{Injection realism:} synthetic injection prompts may not reflect the sophistication of real-world attacks; the group will note this as a threat-model boundary rather than claim comprehensive coverage.
    \item \textbf{Model/API variance:} LLM outputs are non-deterministic and API models may change over the project timeline; mitigated by pinning model versions where possible and running multiple trials per episode.
    \item \textbf{Dual-use consideration:} the project involves designing working prompt-injection attacks. These will be developed and tested strictly within the group's own sandboxed simulation, never against any real third-party service, and will be presented alongside their corresponding defenses rather than as standalone exploits.
    \item \textbf{No real data:} all task content (emails, calendar entries, etc.) will be synthetic — no real personal data, credentials, or private material will be used or included in the report or repository.
    \item \textbf{Fallback plan:} if API costs or time constraints limit the number of defenses/ablations that can be run, the group will prioritize the baseline vs. two defenses and the single-turn vs. delayed-trigger comparison, dropping remaining ablations first.
\end{itemize}
